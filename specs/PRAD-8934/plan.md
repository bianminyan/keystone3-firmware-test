# PRAD-8934 实现计划

需求：[spec.md](spec.md)。本计划补录已有实现，提交顺序按用户要求整理；以下验证状态按实际证据记录。

## 修改方案

### 1. CBOR 流式校验

Rust 仍先重组完整 CBOR，再以最多 228 字节的数据块交给 MPU 沙箱。沙箱只保存跨块解析状态，在最后一块确认结构完整，不再保存第二份完整 CBOR。保留深度、元素数量、截断和尾部数据检查。

沙箱可写区仍为 16 KiB。原 14 KiB 大缓冲区仍供 EIP-712 JSON 使用，不宣称释放了全部 SRAM。Cypherpunk 的完整 CBOR 原本就在 PSRAM，本次没有迁移它的位置。

### 2. 输入限制与预算

重组前检查声明长度、分片数量及会话元数据。Cypherpunk 的 Zcash 单笔和批量上限为 32 KiB，其他路径保留原边界。

统一使用一个分片预算对象，按类型选择额度。重复序号不重复收费；源分片按一个索引估算，混合分片按最大可能索引数估算。每个新序号收费为 `片长 + 索引数估算 × 8 + 128`。该公式是保守资源估算，不是内存峰值测量；过多的新混合片仍可能耗尽额度。

移除 TRON 的重复预算解析，保留其 128 片、192 KiB 及业务长度检查。TRON 单帧 UR 文本上限改为 1536 字节，与通用分片预算一致，不再用完整消息的编码长度推导单帧上限。扫码侧的 1536 字节 C 字符串缓冲区还需预留结尾的 NUL，有效文本最多为 1535 字节。Web3 沙箱 CBOR 传输上限对齐 TRON 的 17 KiB 重组额度（16 KiB sign_data + 1 KiB 元数据）；Cypherpunk 保持 32 KiB，BTC-only 保持 14 KiB。其他类型的分片重组预算及 EIP-712 JSON 缓冲区仍为 14 KiB。

TRON 的重组额度、类型判断及共用文本长度检查统一放在 `common/ur_budget.rs`，删除 `tron/ur_limits.rs`。单条 TRON UR 在解码前复用 1536 字节检查，移除因此已不可触发的单条 CBOR 17 KiB 检查；其他类型单条 UR 的现有入口行为保持不变。

### 3. MPU 与错误处理

启动和调度器初始化使用相同 PSRAM 配置：特权读写、不可执行，沙箱不直接访问 PSRAM。使用可信代码逐块复制输入，保留原超时和失败关闭路径。

分块偏移和总长度必须连续一致。CBOR 会话完成或块序列错误后清理状态，不覆盖其他协议正在使用的联合体。保留失败原因日志，删除临时成功路径大小日志。

## 2026-09-29 MPU 实机验证

用户在测试设备上手动触发两项故障：特权态执行 PSRAM 地址 `0x80080010`，得到 `CFSR=0x00000001`、`PC=0x80080010`；沙箱读取同一地址，得到 `CFSR=0x00000082`、`MMFAR=0x80080010`。两次测试前特权读写均成功，故障后均重启。证据确认 PSRAM 不可执行及沙箱读取被拒绝。临时故障注入命令、沙箱操作和构建开关已移除，不随 PR 交付。

## 2026-09-29 TRON 沙箱入口修正

用户实机扫描 14,337 字节 TRON CBOR，返回 `sandbox CBOR validation unavailable`。Rust 预算允许 17 KiB，但 Web3 C 入口仍限制 14 KiB，导致数据重组后在进入沙箱前被拒绝。此前 TRON 模拟器测试直接调用 Rust 校验器，没有覆盖 C 入口；原计划把这两个不一致的上限保留下来是遗漏。

本地 `test/mpu_sandbox/test_cbor_stream_ipc.py` 现覆盖实际 `MpuSandboxValidateCbor`、分块发送循环及沙箱 C 处理函数，任务调度和 Rust 解析器使用桩。新增 14,337/17,408 字节通过及 17,409 字节拒绝的 Web3 回归，旧代码失败，修正后通过；同时验证 BTC-only 14 KiB、Cypherpunk 32 KiB、错误分块和状态清理。完整 TRON 请求的设备复测仍待完成。
